# 局域网 HTTPS

本文件是局域网 HTTPS 的规则：监听、证书层级、叶证书的自动签发与续期、启动检查、关闭、节点更换和对前端 App 的要求。硬规则摘要见 [HTTP 约定](../engineering/http.md#http-约定)、[「认证」](../../AGENTS.md#认证)；部署步骤与网络加固（业务设备 Wi-Fi 与访客网络隔离、kiosk 浏览器只放行工作站页面、SSH 只用密钥登录）见 [部署要求](../../deploy/README.md)。
随局域网 HTTPS 切片实现。

## 监听

- `listen_addr`：配置了 `[tls]` 时只提供 HTTPS，平板和手机经它访问。局域网上不开明文 HTTP 端口，不做 HTTP 到 HTTPS 的跳转。
  - 只绑定有线网口的固定 IP：`listen_addr` 的 IP 必须等于 `[tls].ip`，否则拒绝启动；不绑定 `0.0.0.0`。
  - 固定 IP 绑定只限制目的地址。部署时还须配置持久化的主机入站防火墙规则：HTTPS 端口只允许从有线业务网口入站，拒绝无线热点及其他接口的入站流量，操作与验证见 [网络与固定 IP](../../deploy/README.md#网络与固定-ip)。
    - 理由：Linux 的本地 IP 属于整个主机，绑定有线 IP 不能单独阻止从无线接口到达该目的地址的流量。
  - 该地址尚未出现在网口上（网口未就绪，或固定 IP 由路由器下发）而绑定失败时不拒绝启动：记 `warn`，每 5 秒重试绑定，期间 `workstation_addr` 照常。
    - 理由：服务只依赖 `network.target`；反复退出重启会触发 systemd 的启动频率限制，服务停在失败状态。
- `workstation_addr`（可选）：明文 HTTP，只供门店机本机的工作站浏览器使用，与 `listen_addr` 提供同一个 `Router`（静态文件 + API）。省略时不开这个端口。
  - IP 必须是回环地址（`127.0.0.0/8` 或 `::1`）；其他地址（包括 `0.0.0.0`、`::` 和门店机的局域网 IP）一律拒绝启动。
    - 理由：工作站只能在门店机本机访问；回环流量不经过网卡，浏览器把回环地址当作安全来源。绑定到其他地址会让 PIN 和令牌以明文出现在局域网上。
  - 只接受 `Host` 的主机部分为 `localhost` 或 `workstation_addr` 的 IP 字面量（IPv6 写成方括号形式，如 `[::1]`）的请求，可以带端口，主机名不区分大小写；例如绑定 `127.0.0.1:8080` 时接受 `127.0.0.1:8080`、`localhost`，绑定 `[::1]:8080` 时接受 `[::1]:8080`、`localhost:8080`。缺少 `Host` 或为其他值时返回 `400 VALIDATION_FAILED`，`details` 为 `{}`。在路由和身份之前判定，对所有路径（含 `/health` 和静态文件）生效；照常记请求日志。
    - 理由：防止 DNS 重绑定：门店机上的网页把攻击者的域名解析到 `127.0.0.1` 后访问工作站端口时，`Host` 是攻击者的域名。
- release 构建没有 `[tls]` 段时拒绝启动。debug 构建省略 `[tls]` 时，`listen_addr` 提供明文 HTTP（开发与锁定测试用），不注册认证接口（[传输加密](../business/auth.md#认证规则)）。
- 不启用 TLS early data（0-RTT）：rustls `ServerConfig` 的 `max_early_data_size` 保持 0。
  - 理由：0-RTT 数据可以被重放。
- 握手失败不进请求日志：请求日志只记进入应用中间件的请求（[Rust](../engineering/rust.md#rust)）。
- 握手失败的日志写进节点自身的日志，与请求日志同一输出：
  - 每次握手失败记一条 `debug`，字段为来源 IP 和本端观察到的失败原因；对端只断开连接时如实记录，不推断为校时信号无效或具体证书问题。
  - 另按时间汇总：每 5 分钟最多一条 `warn`，字段为该时段的失败次数、最近一次失败的来源 IP 和原因；该时段没有失败时不记。
    - 理由：握手失败多由客户端引起（时间错误、未内置根、扫描），逐条记 `warn` 会淹没日志。
  - 握手失败不进 `/health` 的问题清单。

## 请求顺序与错误

- 配置 TLS 的局域网请求先建立网络连接，再完成 TLS 握手与证书验证，然后才进入 HTTP 请求处理。HTTP 内部的身份、权限、幂等和校时检查按 [HTTP 约定](../engineering/http.md#http-约定)的顺序执行；前置检查通过后才执行业务逻辑。
- TLS 握手失败时，App 处理网络库报告的安全连接或证书错误，不发送业务请求内容；没有节点 HTTP 响应，不生成 `CLOCK_NOT_SYNCED`。节点只记录本端观察到的握手失败，不生成该请求的 HTTP 请求日志或业务错误。
- 节点没有监听 HTTPS 端口、连接被拒或连接超时时，App 报告连接失败；不能将这些情况一律归为证书错误。TLS 错误能够可靠细分时显示相应原因，否则显示安全连接失败，不绕过证书校验。
- HTTPS 已建立、HTTP 请求到达节点且命中校时门禁时，返回 `503 CLOCK_NOT_SYNCED`，按请求日志规则记录；前端按 SOP 提示校时。证书恢复后的重试重新经过各阶段，按该次请求实际命中的检查返回结果。
- 节点校时核对与证书签发、续期在各自后台任务中运行，不由业务请求等待或执行；校时不以 HTTPS 可用为前提。签发所需信号无效时，按 SOP 联网校时，信号有效后再签发证书；不要求先收到 HTTP 校时错误才能开热点。
- 后台校时、证书维护任务照常记录自身结果，`/health` 照常反映已知问题；这些状态不冒充某次尚未进入 HTTP 层的请求结果。

## 证书层级

| 证书 | 有效期 | 签发者 | 保管 |
|---|---|---|---|
| 连锁根 | 20 年，ECDSA P-256 | 自签 | 私钥口令加密，存两只 U 盘分开离线保存，由维护门店机的人保管，写进维护交接；根证书内置 App |
| 门店签发 CA | 5 年 | 连锁根，部署时由维护人员离线签发 | 每店一张；私钥在门店节点上生成，不离开节点 |
| 叶证书 | 90 天（上限见下） | 门店签发 CA，由节点自动签发 | 私钥由节点生成，只在节点上 |

- 门店签发 CA：`basicConstraints` CA、`pathLen = 0`；名称约束（critical）permitted 为 `DNS:<store_id>.node.fengyan.internal`、`IP:10.0.0.0/8`、`IP:172.16.0.0/12`、`IP:192.168.0.0/16`。
  - 门店之间的隔离由 App 固定本店门店签发 CA 的指纹承担（见[「对前端 App 的要求」](#对前端-app-的要求)）；名称约束保留，但不作为隔离门店的依靠。
- **本店 CA 指纹**：门店签发 CA 证书中 SubjectPublicKeyInfo（DER）的 SHA-256，写成 64 位小写十六进制。部署时记进部署记录，经 MDM 托管配置下发给本店的平板和手机。
- 生成与签发流程（节点上生成私钥和 CSR，维护人员在专用离线签发机上用根加名称约束签发）见 [门店签发 CA](../../deploy/README.md#门店签发-ca)。
- 叶证书：
  - 密钥 ECDSA P-256；EKU `serverAuth`；签发者名称取门店签发 CA 证书中的主题原文。
  - SAN：`IP:<[tls].ip>`、`DNS:<store_id>.node.fengyan.internal`。`ip` 是部署记录中门店节点的固定 IP。
  - `notBefore = now − 1 天`；`notAfter = min(now + 90 天, 门店签发 CA 的 notAfter)`。
    - 理由：CA 过期后整条链失效，叶证书更长的有效期没有意义，还会让 `tls_cert_not_after` 误导提醒。
  - `now` 取时钟模块的读数，与同一次判断中的节点信号判定是同一次读数。

## 叶证书的签发与续期

**可加载**：叶证书能解析、与叶私钥配对、由当前配置的门店签发 CA 签发、IP SAN 等于配置的 `ip`。启动时检查文件；运行中检查内存里正在使用的证书，不因持久化失败留下的不配对文件而丢弃内存证书。

**可用**：可加载，且按本次节点时钟读数在有效期内。可加载但尚未生效或已过期的现有证书仍可加载、保留；客户端按自己的时钟验证证书链并决定是否接受。节点的健康状态按 [健康状态](runtime.md#健康状态get-health)报告。

**签发条件**：节点校时信号有效，且同一次时钟读数满足门店签发 CA 的 `notBefore ≤ now < notAfter`。所有叶证书的首次签发、重新签发和续期都必须满足此条件，持久化成功后才加载；不签发临时证书。

- 启动时：
  - 有可加载的叶证书：加载它。
  - 没有当前可用证书时，只有满足签发条件才签发：签发叶证书，持久化后加载。
  - 不满足签发条件，或签发、持久化、加载失败：保留当前证书（如有）；没有当前证书时 `listen_addr` 暂不监听。节点校时任务与 `workstation_addr` 照常，证书续期任务继续判断。
- 运行中由续期任务每 1 分钟重新判断 CA 与当前证书（间隔按单调时间计）：
  - 没有当前可用证书时，只有满足签发条件才签发：签发叶证书，持久化后加载或替换；此恢复分支不要求新 `notAfter` 晚于旧值，覆盖校时回拨后当前证书尚未生效的情况。
  - 当前证书仍可用、剩余有效期 ≤ 30 天、满足签发条件，且新证书的 `notAfter` 会晚于现有证书：签发叶证书，持久化后替换。
    - 门店签发 CA 剩余不足 30 天时，新证书的 `notAfter` 与仍可用的现有证书相同，不再重签，直到更换门店签发 CA。
  - 不满足相应签发条件时保留当前证书（如有），下一次判断继续检查；信号无效或 CA 按节点时钟尚未生效、已过期时不签发任何叶证书。
- 证书加载后，尚未启动的 HTTPS 监听随之启动；地址尚未就绪时进入每 5 秒绑定重试。证书替换经 `RustlsConfig` 重新加载，不重启进程。
- 密钥生成和签名在 `spawn_blocking` 中执行，不进入 `Writer::call` / `Readers::call` 闭包。
- 例：节点时钟被重置、校时信号无效且叶证书文件损坏时，HTTPS 暂不监听。店长按 SOP 打开热点，后台校时成功后，下一次证书任务判断签发并持久化叶证书，启动 HTTPS；App 重试后再经过 HTTP 前置检查。

**持久化**：叶证书与叶私钥写在 `[tls].cert_dir`（示例 `/var/lib/boh/tls`）中的 `node.key`、`node.crt`（PEM：叶证书在前，随后是门店签发 CA 证书）。

- 启动时 `cert_dir` 不存在则创建（权限 0700）；创建失败或不是目录时拒绝启动。`node.key` 权限 0600。
- 写入顺序：写私钥临时文件 → fsync → 重命名为 `node.key` → 写证书临时文件 → fsync → 重命名为 `node.crt` → fsync 目录。全部成功才替换正在使用的证书。
  - 任一步失败：记 `error`，继续使用当前证书；没有当前证书时保持 HTTPS 暂不监听、工作站照常。下一次满足签发条件时重新执行全部步骤。
  - 中途断电留下不配对的文件时，下次启动按「可加载」判定发现；满足签发条件后重签。
- 叶证书和叶私钥不写进数据库，不放在 `backup_dir` 中，不进备份。

**日志**：签发、替换记 `info`；签发或持久化失败记 `error`，在续期任务中记录一次，附失败阶段（生成密钥、签发、写私钥、写证书、目录 fsync、重新加载）。

## 配置与启动检查

```toml
listen_addr = "192.168.1.20:8443"   # IP 等于 [tls].ip
workstation_addr = "127.0.0.1:8080"

[tls]
ip = "192.168.1.20"
ca_cert_path = "/run/credentials/boh.service/store-ca.crt"
ca_key_path = "/run/credentials/boh.service/store-ca.key"
cert_dir = "/var/lib/boh/tls"
```

- `[tls]` 的四项都必填。`ip` 是 IPv4 地址，必须在门店签发 CA 名称约束的三个私有网段内。`ca_key_path` 是 PKCS#8 PEM 私钥。
- 门店签发 CA 的证书和私钥部署在 `/etc/boh/tls/`（root，0600），经 systemd `LoadCredential=` 以只读方式交给服务（`deploy/boh.service`）。
  - 理由：`DynamicUser=yes` 的 UID 启动前未知，无法预先改属主；凭据文件权限是 0440，程序不检查「必须 0600」。
- 拒绝启动：
  - release 构建没有 `[tls]`；
  - `[tls]` 字段缺失或取值非法；
  - `listen_addr` 的 IP 不等于 `[tls].ip`；
  - `workstation_addr` 不是回环地址；
  - 门店签发 CA 的证书或私钥读不了、解析失败、私钥与证书不匹配；证书不是 CA，或没有名称约束；
  - `cert_dir` 创建失败或不是目录。
- 不拒绝启动：门店签发 CA 按节点时钟已过期或尚未生效、叶证书不可用、首次签发或持久化失败、`listen_addr` 的地址暂时绑定不上（见[「监听」](#监听)）。地址尚未就绪按[「监听」](#监听)记 `warn`；其他上述失败记 `error`。由 `/health` 的 `TLS_NOT_READY` 及证书期限问题报告（[健康状态](runtime.md#健康状态get-health)）。
  - 理由：节点时钟本身可能是错的；进程照常启动，查询、校时和工作站尽量可用。
- 叶证书的 `ip` 与配置不符时不加载；改 `ip` 后重启服务，满足签发条件后重签。

## 时间

- 证书有效期由平板按自己的系统时钟核对；平板由 MDM 强制自动设置时间（[前端校时](../business/time.md#前端校时)）。
- 节点签发证书只经时钟模块读时间。rustls `ServerConfig` 的 `time_provider` 注入时钟模块提供的实现。
- `time`、`x509-parser` 中读系统时间的方法由 `clippy.toml` 禁用（[Rust](../engineering/rust.md#rust)）。

## 关闭

- 「停止接收 HTTP」一步同时停止 `listen_addr` 和 `workstation_addr`（`axum-server` 的 `Handle` 优雅关闭）。
- 续期任务：等待下一次判断的间隔直接取消；已经开始的签发与持久化执行完再退出（`spawn_blocking` 开始运行后不能中止）。

## 节点更换与门店签发 CA 更换

- 节点更换（含门店机重装、疑似被攻破）：
  1. 新机器生成新的门店签发 CA 私钥与 CSR，由连锁根的保管人签发新的门店签发 CA；`ip` 保持部署记录中的地址。
  2. 把新 CA 的指纹记进部署记录，经 MDM 把本店的托管配置**改为只有新指纹**，逐台确认平板和手机已经应用。旧 CA 签的证书只在完成更新的设备上不再被 App 接受；未确认的设备暂停使用，恢复连接前先核实配置。
  3. App 内置的根不变；TLS 方面平板不需要重新注册。认证状态按[「门店节点恢复」](../domain.md#尚未设计动手前先讨论)的原则处理。
  - 新的门店签发 CA 装好、MDM 指纹更新之前平板无法连接，门店按 [门店节点宕机](sop.md#门店节点宕机)纸面登记。
  - 旧的门店签发 CA 不吊销，靠 App 不再接受它的指纹失效；旧硬盘报废时物理销毁（[节点更换与硬盘报废](../../deploy/README.md#节点更换与硬盘报废)）。
- 门店签发 CA 到期更换（5 年一次）：先经 MDM 在托管配置中加入新指纹（新旧并存），逐台确认本店平板和手机已应用，再在节点上替换 CA 文件并重启；确认设备能连上后，从托管配置中删除旧指纹，并逐台确认删除已生效。
  - MDM 已下发不代表设备已应用。未收到配置的离线设备保留原配置，不算完成更新；确认结果写进部署记录。

## 对前端 App 的要求

- 根证书内置 App，作为唯一的信任锚：
  - Android：Network Security Config 的 `<base-config>` 中 `<trust-anchors>` 只列内置根，不列 `system`、`user`。
  - iOS：在 URLSession 的服务器信任挑战中以内置根调用 `SecTrustSetAnchorCertificates`，再 `SecTrustEvaluateWithError`；失败时取消挑战。Info.plist 写 `NSLocalNetworkUsageDescription`。
- 固定本店门店签发 CA：链验证通过之后，再要求链中门店签发 CA 的指纹等于 MDM 托管配置下发的本店指纹之一，否则拒绝连接。
  - 托管配置可以列多个指纹（门店签发 CA 到期更换时新旧并存），平时只有一个。托管配置缺失或为空时拒绝连接。
  - 指纹只把「本店哪张 CA」固定下来，信任仍来自连锁根签名链。
- 按部署记录中的门店节点 IP 访问 `https://<ip>:<端口>`，用平台标准的主机名校验（核对 IP SAN）；不另做叶证书固定，不写自定义名称校验。
- 以下情况都必须拒绝连接，不发送任何请求内容：
  - 自签证书，或链接不到内置连锁根；
  - 链中任何一张证书按设备时钟已过期或尚未生效；
  - 门店签发 CA 的指纹不在本店托管配置中（换了 CA 而托管配置未更新、其他门店的 CA）；
  - 叶证书的 IP SAN 不等于所连的 IP。
- TLS 握手失败按[提交状态](../business/command-submission.md#1-提交状态app)中的「未发出」处理。

## 实现

- TLS 用 `rustls`（`ring`），HTTPS 监听用 `axum-server`，PEM 读取用 `rustls-pki-types`，叶证书签发用 `rcgen`（见 [技术栈](../engineering/architecture.md#技术栈已定不要替换)）。
- 叶证书的签发与续期在 `boh-app`，进程装配在 `boh-server`。
- 切片的第一个提交先用 `cargo zigbuild --release` 实测 `x86_64-unknown-linux-musl` 和 `aarch64-unknown-linux-musl` 两个目标。

## 与上行同步的关系

- 上行同步的 mTLS 沿用同一个连锁根：节点访问总部的客户端证书由单独的「门店客户端签发 CA」签发（EKU `clientAuth`），用单独的私钥，不与局域网服务器证书共用。
- 总部同步接口的服务器证书来源随上行同步设计定。
